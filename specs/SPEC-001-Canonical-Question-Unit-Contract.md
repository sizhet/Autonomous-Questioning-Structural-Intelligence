# SPEC-001 — Canonical Question Unit Contract

**Project:** Autonomous Questioning Structural Intelligence (AQSI)  
**Version:** 1.0.0 (research specification)  
**Status:** Proposed; not an implemented or certified standard  
**Scope:** Canonical representation, identity, provenance, lifecycle, evidence, scoring references, and relay interoperability for a Question Unit (QU).

## Abstract

A Question Unit (QU) is a persistent, typed, provenance-bearing research object rather than a transient prompt. This specification proposes a minimal interoperable contract for representing questions generated by humans, language models, structural inference, historical retrieval, and cross-domain relay. It separates question identity from its textual expressions; records multi-granularity structural features without requiring a single universal ontology; and supports evidence, uncertainty, revisions, lifecycle transitions, and governance. It defines normative requirements for conforming producers, consumers, and relay systems, plus example records and validation tests. It does not claim that a particular question-scoring model, UTN implementation, or autonomous research system has been empirically validated.

## 1. Purpose and boundaries

The QU contract enables an AQSI system to:

1. Preserve the identity of a research question across prompt reformulations and execution adapters.
2. Record how the question arose and which structural observations support its formulation.
3. Link question attributes, methods, constraints, residuals, and evidence using typed references.
4. Track historical assessments and exploration outcomes without confusing predicted value with observed value.
5. Transfer question objects among agents and domains with explicit semantic alignment and provenance.
6. Permit independent conformance testing before implementing autonomous execution.

This specification **does not** prescribe a particular language model, scoring function, differential-tree implementation, storage engine, UTN registry, or governance policy. An exploration authorization is separate from the QU itself and MUST NOT be inferred from a high question score.

## 2. Normative language and terminology

**MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** denote proposed interoperability requirements for implementations claiming conformance to this research specification.

- **Question Unit (QU):** A versioned record for one research question and its associated structural and evidentiary context.
- **Question family:** A set of related QUs linked by a common structural core and typed deltas.
- **Question expression:** A human-readable question, prompt, API request template, SQL query, or formal statement derived from a QU.
- **UTN reference:** A typed, namespaced identifier with an explicit semantic interpretation and optional registry resolution.
- **Structural factor:** A typed concept, attribute, method, constraint, evidence item, residual, or relation used in question discovery and scoring.
- **Evidence record:** A source-grounded claim, observation, experiment, or counterexample with an explicit epistemic status.
- **Relay:** A provenance-preserving transfer, derivation, composition, replication, or transformation of research artifacts.
- **Explicit leftover:** An unresolved issue retained for future exploration rather than silently discarded.

## 3. Contract design principles

### 3.1 Identity is not wording

A QU's stable identifier MUST remain independent of any single natural-language formulation. Material changes to the research proposition SHOULD create a new QU linked by `derived_from` or `reframes`, rather than silently reusing the old identity. Corrections that preserve the proposition MAY increment the record revision.

### 3.2 Open representations with typed boundaries

A QU MAY refer to multiple representations (natural language, differential trees, graphs, constraints, embeddings, formal models). Each representation MUST declare its type and schema or interpretation reference. An unknown relationship MUST be represented as unknown or unassessed, not automatically scored as zero.

### 3.3 Evidence and hypotheses remain distinct

Predictions, agent opinions, simulations, observations, and independently reproduced results MUST have distinguishable evidence types. A question's estimated potential MUST NOT be presented as verified research impact.

### 3.4 Relay preserves provenance

Transformations MUST retain references to source artifacts, operation type, responsible actor or process, and transformation time. A relay recipient MUST be able to distinguish a copied assertion from a newly validated result.

### 3.5 Contracts before execution

QU validation and exploration authorization are separate checks. Passing the former MUST NOT imply permission to run an experiment, access external data, spend funds, or change system policy.

## 4. Canonical Question Unit schema

The following is a **logical schema**. A future JSON Schema, Protocol Buffers definition, or typed database schema MAY realize it. The `required` column applies to the canonical record, not to every early-stage discovery fragment.

| Field | Required | Type | Semantics |
|---|---|---|---|
| `contract` | Yes | string | `aqsi.question-unit/1.0` |
| `question_id` | Yes | URI/URN string | Stable globally scoped QU identity |
| `revision` | Yes | integer ≥ 1 | Monotonic revision of the same proposition |
| `created_at` | Yes | RFC 3339 timestamp | Initial creation time |
| `updated_at` | Yes | RFC 3339 timestamp | Latest record update time |
| `origin` | Yes | object | Origin kind, actor/process reference, source references |
| `canonical_question` | Yes | object | Primary language, question text, proposition scope |
| `status` | Yes | enum | Lifecycle state, Section 9 |
| `domain_refs` | Yes | array | Zero or more typed domain references; empty allowed |
| `structural_factors` | Yes | array | Multi-granularity typed factors; empty at intake allowed |
| `representations` | Yes | array | Optional alternative structural or linguistic forms |
| `relations` | Yes | array | Typed references to other QUs and artifacts |
| `evidence_refs` | Yes | array | References to evidence records |
| `assessment_refs` | Yes | array | References to independently versioned assessments |
| `governance` | Yes | object | Visibility, sensitivity, policy references, execution authorization state |
| `leftovers` | Yes | array | Explicit unresolved issues |
| `extensions` | No | object | Namespaced extension data |

An intake producer MAY omit some arrays in a *draft fragment*, but a canonicalizing producer MUST materialize all required fields before declaring the QU conformant.

### 4.1 Origin

`origin.kind` SHOULD be one of `human`, `llm`, `structural_inference`, `historical_retrieval`, `cross_domain_transfer`, `relay`, or `other`. `origin.actor_ref` identifies the originating person, agent, or system where disclosure is permitted. `origin.source_refs` links motivating artifacts. If the true source is unavailable, `origin.kind` MUST be `other` and the uncertainty MUST be recorded; a fictitious source MUST NOT be inserted.

### 4.2 Canonical question

`canonical_question.text` MUST be nonempty. `canonical_question.language` SHOULD use a BCP 47 tag. `canonical_question.scope` MAY specify assumptions, variables, target domain, exclusions, and success conditions. A question is not required to be answerable by a single LLM call.

### 4.3 Structural factors

Each factor MUST include `factor_id`, `kind`, `type_ref`, and `value_ref` or `value`. Suggested `kind` values: `concept`, `attribute`, `method`, `constraint`, `observation`, `evidence`, `counterevidence`, `residual`, `transfer_point`, `relationship`, `question`, `other`. Additional factor properties MAY include granularity, confidence, uncertainty, applicability conditions, and evidence references. Confidence is not a substitute for evidence quality.

### 4.4 Typed relations

Each relation MUST specify `predicate`, `target_ref`, and `direction`. Suggested predicates include `derived_from`, `reframes`, `splits`, `composes`, `transfers_from`, `contradicts`, `supports`, `depends_on`, `replicates`, and `revisits`. Relation semantics MUST NOT be inferred solely from a natural-language label. Cross-domain links SHOULD cite an alignment record or explain why alignment is provisional.

## 5. UTN identity and semantic alignment

A conforming QU MUST have a stable `question_id`; it SHOULD also have an optional `utn_ref` whose namespace and type are resolvable or documented. Implementations MAY use locally scoped identifiers while offline, provided a deterministic migration mapping is retained when federating.

A UTN reference SHOULD declare:

- namespace and local identifier;
- entity or relation type;
- semantic version or contract reference;
- domain scope and granularity;
- alias or equivalence status where relevant;
- provenance of the mapping.

**Same spelling does not imply semantic equivalence.** A mapping SHOULD distinguish `equivalent`, `broader`, `narrower`, `analogous`, `incompatible`, and `unknown`. Transfer of a historical score across domains MUST be marked as an estimate unless independently validated in the target domain.

## 6. Representations and question differential trees

Each `representations[]` entry MUST declare `representation_id`, `kind`, and either `payload_ref` or an inline `payload`. Examples include `natural_language`, `prompt_template`, `formal_proposition`, `differential_tree`, `structural_graph`, `sql_template`, and `experiment_design`.

A differential-tree representation SHOULD identify a reusable `core_ref`, typed `delta` operations, and a transformation provenance record. A tree is not mandatory: other representation families MAY coexist. When two representations disagree, the producer MUST retain the conflict or designate one as superseded with an explanation; it MUST NOT silently merge incompatible propositions.

## 7. Historical assessments and directional influence

Scores MUST be stored as separate, versioned **assessment records**, referenced through `assessment_refs`. Each assessment SHOULD identify:

- `assessment_id`, scorer/model version, and timestamp;
- target QU or ordered QU pair;
- assessment kind, e.g. `historical_potential`, `directional_influence`, `novelty`, `feasibility`, `cost`, `risk`, `observed_outcome`;
- score scale, orientation, and calibration context;
- uncertainty or `unknown` status;
- supporting evidence and provenance;
- policy or perspective context, if relevant.

For ordered influence, `source_question_id` and `target_question_id` MUST be explicit. `I(q_i → q_j)` MUST NOT be assumed equal to `I(q_j → q_i)`. Missing evidence MUST NOT be interpreted as a zero-valued influence. Scores from different scales MUST NOT be aggregated without a documented normalization or folding contract. Historical failure MAY justify deferral but MUST NOT automatically impose permanent exclusion on structurally novel candidates.

## 8. Evidence, counterevidence, and epistemic status

Evidence records SHOULD include `evidence_id`, `claim_ref`, `kind`, `source_ref`, `collected_at`, `method_ref`, `epistemic_status`, and `limitations`. Recommended statuses include `hypothesis`, `model_generated`, `inferred`, `observed`, `experimentally_tested`, `independently_replicated`, `refuted`, and `unknown`.

A producer MUST NOT label an LLM-generated answer as an independently replicated result. Contradictory evidence MUST remain accessible, including when an assessment is revised. Sensitive sources MAY be redacted, but the redaction and its implications for verification MUST be recorded. Evidence lineage SHOULD be traversable from the QU to the original source where authorized.

## 9. Lifecycle contract

The proposed canonical lifecycle states are:

`candidate → evaluated → selected → exploring → explored → relayed`

Additional states: `deferred`, `blocked`, `revisit_pending`, `retired`.

| From | To | Minimum condition |
|---|---|---|
| `candidate` | `evaluated` | Assessment or documented inability to assess |
| `evaluated` | `selected` | Portfolio decision reference and governance check |
| `evaluated` | `deferred` | Reason and review trigger |
| `selected` | `exploring` | Separate valid exploration contract and authorization |
| `exploring` | `explored` | Outcome, limitations, and unresolved issues recorded |
| `explored` | `relayed` | Relay artifact and lineage recorded |
| `deferred` | `revisit_pending` | New evidence, policy change, or scheduled review |
| `revisit_pending` | `evaluated` | Reassessment recorded |
| any nonterminal state | `blocked` | Governance or safety restriction with reason |
| `blocked` | `evaluated` | Authorized review and removal of restriction |
| any state | `retired` | Recorded rationale and retention policy |

An implementation MAY define additional transitions, but MUST publish them in a versioned extension. State transitions MUST be recorded as append-only events or an equivalent auditable history. `selected` MUST NOT imply `authorized`.

## 10. Governance and authority

The `governance` object MUST distinguish at least `visibility`, `policy_refs`, and `execution_authorization`. Suggested authorization values: `not_requested`, `pending`, `approved`, `denied`, `expired`, and `revoked`. The canonical QU itself does not grant approval; approval MUST reference an external authorization decision with scope and validity period.

Policy may constrain resource budgets, permitted tools, data access, privacy, research direction, and prohibited operations. A scoring model MAY recommend a question but MUST NOT override human-defined policy boundaries or create its own authority to execute. Policy changes SHOULD be auditable and attributable.

## 11. Relay and revision semantics

A relay operation MUST record `operation_id`, `operation_type`, `input_refs`, `output_refs`, `actor_ref`, and `timestamp`. It SHOULD record a transformation contract, alignment assumptions, and any loss of information. Operations MAY include `derive`, `split`, `compose`, `transfer`, `refute`, `revisit`, `replicate`, `fold`, and `unfold`.

- **Revision** changes metadata or representation while preserving the underlying research proposition.
- **Derivation** creates a new question proposition and therefore a new `question_id`.
- **Replication** re-executes an exploration and may produce new evidence without creating a new question.
- **Transfer** creates a target-domain QU when domain-specific assumptions materially change.

Repeated execution counts as meaningful relay only when its observations, provenance, or reproducibility information are captured; merely rerunning an identical process without recording new information is not evidence of knowledge growth.

## 12. Illustrative canonical QU (YAML)

This is a **non-executable illustrative record**; identifiers and results are hypothetical.

```yaml
contract: aqsi.question-unit/1.0
question_id: urn:aqsi:question:example:Q-0042
revision: 1
created_at: '2026-10-28T00:00:00Z'
updated_at: '2026-10-28T00:00:00Z'
origin:
  kind: structural_inference
  actor_ref: urn:aqsi:agent:example:discoverer
  source_refs:
    - urn:aqsi:artifact:example:gap-17
canonical_question:
  language: en
  text: Can historical failed questions identify transferable missing methods in a new domain?
  scope:
    assumptions:
      - Comparable structural factors can be identified with uncertainty.
    exclusions:
      - No claim of proven cross-domain performance.
status: candidate
domain_refs:
  - urn:utn:example:domain:software-engineering
structural_factors:
  - factor_id: f-1
    kind: residual
    type_ref: urn:utn:example:type:unresolved-method-gap
    value: Missing method for a recurring class of failures
    granularity: method
  - factor_id: f-2
    kind: transfer_point
    type_ref: urn:utn:example:type:cross-domain-analogy
    value: Candidate analogy from a historical question family
    granularity: relationship
representations:
  - representation_id: r-1
    kind: natural_language
    payload: Can historical failed questions identify transferable missing methods in a new domain?
relations:
  - predicate: derived_from
    target_ref: urn:aqsi:artifact:example:gap-17
    direction: incoming
evidence_refs: []
assessment_refs: []
governance:
  visibility: public
  policy_refs: []
  execution_authorization: not_requested
leftovers:
  - leftover_id: l-1
    description: Define a falsifiable transfer benchmark and negative controls.
    status: open
extensions: {}
```

The sample deliberately has no empirical score or outcome. `urn:utn:example:*` is an illustrative reference, not a claim that a live UTN registry exists.

## 13. Validation and conformance rules

A conforming **QU producer** MUST satisfy C-001 through C-010; a **QU consumer** MUST satisfy C-001, C-003, C-006, C-008, and C-010 when reading or transforming records. A **relay producer** MUST additionally satisfy C-011 and C-012.

| ID | Requirement | Suggested negative test |
|---|---|---|
| C-001 | Required canonical fields and correct contract version | Missing `question_id` |
| C-002 | Stable ID and monotonic revision | Same ID reused for a materially different question |
| C-003 | Nonempty question text and explicit language | Blank question text |
| C-004 | Typed structural factors and representation references | Factor with no `kind` or `type_ref` |
| C-005 | Provenance recorded or explicitly unknown | Invented source reference |
| C-006 | Evidence status distinct from model prediction | Model answer marked independently replicated |
| C-007 | Assessment provenance, scale, and direction | Unlabeled asymmetric pair score |
| C-008 | No implicit execution authorization | `selected` interpreted as permission to execute |
| C-009 | Auditable lifecycle transitions | `candidate` silently becomes `explored` |
| C-010 | Unknown relation not silently treated as zero | Missing influence filled with zero by default |
| C-011 | Relay input/output lineage and operation type | Derived question with no parent link |
| C-012 | Cross-domain mapping uncertainty preserved | Analogous mapping asserted equivalent without justification |

A validation report SHOULD include the tested contract version, producer or consumer version, test cases, failures, exceptions, and whether checks were static or exercised in a runtime. This document proposes tests; it does not report that any implementation passed them.

## 14. Compatibility and schema evolution

The contract string uses `major.minor` versioning. Backward-compatible additive fields MAY increase the minor version; changes that invalidate existing required fields or semantics MUST increase the major version. Unknown namespaced extension fields SHOULD be preserved by relay systems when feasible, but consumers MUST NOT assume they understand an unrecognized extension. Migration MUST preserve provenance and explicitly record lossy transformations.

## 15. Security, privacy, and research integrity

Question records can reveal unpublished hypotheses, private data, organizational strategy, or sensitive experiment plans. Implementations SHOULD apply least-privilege access, controlled disclosure, audit logging, retention policies, and source integrity checks. A public relay MUST NOT leak protected data merely because a question itself is public. Input text, linked artifacts, and LLM outputs MUST be treated as untrusted for execution purposes. An external tool call requires independent authorization and validation.

## 16. Worked lifecycle example

A system observes repeated failures in a software-testing workflow and creates a `candidate` QU with a residual factor. A historical retriever finds related failed and successful questions, producing *assessment references* rather than overwriting the question text. The candidate becomes `evaluated`. A portfolio controller may select it because it complements other questions, but the system still requests a separate exploration contract before entering `exploring`. A bounded experiment produces inconclusive evidence and a new method-gap question. The original QU becomes `explored`, with an explicit leftover; the new QU receives a new identity and `derived_from` link. Both artifacts may be relayed to a different domain only after the alignment uncertainty is documented. No successful transfer is presumed.

## 17. Testable hypotheses and evaluation plan

- **H1 — Provenance:** QU-conformant relay reduces loss of question lineage versus prompt-only logs.
- **H2 — Identity:** Stable QU identity improves duplicate detection across paraphrases without collapsing materially different propositions.
- **H3 — Evidence discipline:** Explicit epistemic status reduces the rate at which model-generated claims are mistaken for validated findings.
- **H4 — Transfer:** Typed cross-domain alignment reduces unsupported analogy claims versus untyped text matching.
- **H5 — Lifecycle:** Explicit deferral and revisit states improve recovery of historically low-ranked but later useful questions.
- **H6 — Governance:** Separate authorization checks reduce unauthorized exploration transitions relative to score-triggered execution.

Evaluate against plain prompt logs, untyped JSON records, and question records without historical lineage. Measure provenance completeness, semantic drift, false equivalence, lifecycle violations, unauthorized action attempts, inter-annotator agreement, and overhead. Use blind review, negative controls, and ablation studies. Publish failures and counterevidence, not just favorable results.

## 18. Open issues

1. What is the minimum interoperable UTN reference contract when no shared registry exists?
2. How should question identity be defined for semantically near-equivalent but experimentally distinct formulations?
3. Which structural factors warrant canonical types, and which should remain domain extensions?
4. How should delayed descendant value be attributed without double counting?
5. What uncertainty model best supports cross-domain assessment transfer?
6. How can protected evidence be audited without disclosing confidential sources?
7. Which lifecycle transitions should be standardized versus left to research-specific governance?
8. How should provenance survive compression, folding, and partial relay?

## 20. Conclusion

The Canonical Question Unit Contract defines a proposed portable research object for AQSI: a question with stable identity, typed multi-granularity structure, traceable origin, separable assessments, explicit evidence status, governed lifecycle, and relay lineage. Its primary value is not a claim of improved intelligence by itself, but the creation of testable interfaces through which autonomous questioning systems can be compared, audited, composed, and improved. Whether these interfaces improve research quality, transfer, and collective learning remains an empirical question.
